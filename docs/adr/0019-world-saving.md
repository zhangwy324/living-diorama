# ADR 0019: World saving

- **Status:** Accepted
- **Date:** 2026-10-28
- **Context:** Roadmap §3.2 step 6, planned as M15. Since step 5 ([ADR 0018](0018-living-behavior.md)) creatures carry individual state (needs, home, knowledge, variation) that is lost on every launch: the world starts fresh with three mosslings, and drawn creatures must be added back from the library (ADR 0009 §12, ADR 0014 §8). Step 6 saves the world and its individuals and restores them on the next launch, including the real-time catch-up that ADR 0018 §19 left for this step. The decisions below were agreed with the owner on 2026-10-28. Step 6 lands as a series of PRs: **0** this ADR; **1** the world save schema (§2); **2** engine save and restore (§7, §8); **3** catch-up (§5, §6); **4** the save and restore protocol messages; **5** the Rust world store (§1); **6** app wiring (§3, §4, §9, §11); **7** tools, soak and the manual checklist. Each PR adds an "as built" note below where it departs from this ADR. All PRs have landed (#103–#105, #107, #109, #111, #115 and #116), so the decisions below, as amended, describe the code. The owner's hand check (the manual checklist in [development](../development.md)) passed on 2026-10-28, and step 6 is not released (§12).

This ADR amends ADR 0018 §19 (short gaps, §6) and, once PR 6 lands, ADR 0008 §14 (the quit timeout, §4) and ADR 0009 §12 (no world persistence). It departs from the spec's persistence suggestion (spec §10.1, §13.2 and §14 question 20; see §1).

## Decisions

### Storage

1. **One JSON file, stored by Rust, checked by TypeScript.** The world is saved as `world.json` in the app data directory, with the previous save kept as `world.prev.json`. Rust writes it atomically, as `settings.rs::write_json` does (a temporary file, then a rename), and doesn't interpret its contents, like the species library (ADR 0014 §3). TypeScript validates it. In development builds `LIVING_DIORAMA_DEV_DATA_DIR` moves it, as it moves the library, so manual checks never touch the player's world.

   **The backup.** Rust falls back to `world.prev.json` only when `world.json` is missing, too large, not UTF-8 or not valid JSON. A `world.json` that is valid JSON but fails validation starts a fresh world (§7), and the backup is not tried. A save never rotates an unreadable `world.json` over the backup.

   **Departure from the spec.** The spec proposes SQLite plus an asset directory, not final (spec §10.1, §13.2, §14 question 20), and the roadmap's backlog lists a `persistence` package for it. Step 6 needs neither: there is one world, its save is small, and it is written whole. A JSON file reuses the atomic write and the Rust-stores/TypeScript-validates split the settings and the library already have. There is no SQLite and no `persistence` package now; the question is revisited with step 7, when the world becomes a base world plus edits. Backups are the one previous save. Checksums and migrations are not adopted: a file that isn't valid JSON falls back to the backup, one that fails validation starts fresh (§7), and backward compatibility is not required (AGENTS.md).

2. **The save schema lives in `content-schema`.** It replaces the stale `CreatureInstanceSchema` (which ADR 0018 §16 said would be widened in step 6) with a strict world save schema matching `CreatureState`. A creature's action state and each behavior's memory stay `unknown` in the schema; the code that owns them validates them.

### Save contents

At least:

- the save version;
- when it was saved (`savedAt`, milliseconds since the epoch);
- the world's ID and version;
- the seed (§8), the tick, the time of day (`minutes`) and the day phase (`dayPhase`; both are needed, or loading a save would emit a spurious phase change, ADR 0018 PRs 3a and 3b);
- the world RNG state and the creature ID counter;
- the world's `introducedSpecies` set, kept so `species_introduced` doesn't fire again for a species after a restore, and the species dependencies (ID and version);
- the creatures, each with its full `CreatureState` (species ID and version, position, needs, home, knowledge, variation, action and behavior memory).

### Lifecycle

3. **Startup order.** `init` creates an empty world. The library then opens and registers drawn species as today (ADR 0014 §8). Then a new `restore` command loads the save. It carries the current wall-clock time, from which the gap is computed, because the simulation never reads a clock (ADR 0006 §1). The three starting mosslings spawn only when there is no usable save. So a restored world never gains extra mosslings, and every drawn species a save names is registered before the save is read.

4. **When to save.** On quit, every 60 seconds, and after a creature is spawned, despawned or released from the Studio. The quit timeout (ADR 0008 §14) rises from 1 second to about 3, so a save on quit can finish; PR 6 measures how long a save takes and records it.

   _Known limitation:_ while the strip is hidden, WebView2 throttles the 60-second autosave timer, so the save can fall minutes behind until quit ([issue #117](https://github.com/zhangwy324/living-diorama/issues/117)); the save on quit still runs.

### Catch-up

5. **A `catchUp` hook on behaviors.** `BehaviorProvider` gains an optional `catchUp(observation, gap)` hook, like the `interrupted` hook on actions (ADR 0018, PR 5a). `core:feed` resets hunger (to a random value below `actAt`, ADR 0018 §19). `core:rest` sets tiredness and can ask for the creature to start sleeping at home, already arrived and asleep. The engine owns the rest: the 12-hour cap, computing the gap, dropping the action in progress, placing awake creatures and suppressing per-creature events. The engine never branches on content IDs; it calls whichever behaviors declare the hook.

   _Amended (owner, 2026-10-28, M15 PR 3):_ catch-up moves the tick on by the capped gap, so every tick-based timer (the release grace, cooldowns, when places were last seen) counts the time away.

6. **Short gaps are no gap (amends ADR 0018 §19).** ADR 0018 §19 said a gap under 2 minutes "runs as ordinary ticks". The clock drops time beyond `maxCatchUpTicks` (ADR 0006 §1), so those ticks would never run. Instead, a gap under 2 minutes is treated as no gap: the world is restored exactly, and only the time of day jumps to the present. A clock that went backwards still counts as no gap, and custom day mode still has no catch-up.

### Compatibility

7. **A save that doesn't match.** The whole save is discarded, with a logged warning, and the world starts fresh when its world ID or world version differs from the running world's, or its save version isn't the current one. The same holds for a save that is valid JSON but fails the schema: the backup is not tried (§1). Within a save that is kept, a creature whose species is missing, or registered with a different major version, is dropped (ADR 0003 §5: the same major version is compatible). Home and knowledge entries naming placements no longer in the world are pruned; behavior memory that names placements is pruned by its owning code. Pruning runs before catch-up (§5) places creatures. What was dropped is reported. A corrupt, unreadable or incompatible save never crashes the app.

   An exact version match is not required beyond this. ADR 0003 §5 already accepts any species with the same major version, and backward compatibility is not required yet (AGENTS.md), so there are no migrations and no shims: a save from an older build either passes these checks or is discarded.

8. **The seed is kept.** A restored world keeps its saved seed across launches, so restoring and carrying on gives the same run as an unbroken one, given the same later commands and time of day (ADR 0006 §2). PR 2's round-trip test checks this headless: it restores at a tick boundary and takes `minutes` from the save.

### Development and scope

9. **Reset is a dev console hook only.** Development builds get `livingDiorama.world.reset()`, which discards the save and starts a fresh world. There is no player-facing reset (owner's decision).

   _As built (M15 PR 6):_ the reset takes every creature out, spawns the starting creatures and saves, but keeps the world's seed, tick and creature ID counter, so it is not a wholly fresh world. Deleting `world.json` and `world.prev.json` gives one.

10. **OS sleep while running is not caught up.** A wall-clock jump within a session (the machine sleeping with the app open) still drops time as today (ADR 0008 §13); only the time of day jumps. Catching up for it is deferred to [issue #113](https://github.com/zhangwy324/living-diorama/issues/113).

11. **The creature-count override skips the save.** When the count override is set (`VITE_CREATURE_COUNT`, as `pnpm measure` does), the app neither loads nor writes the save, so measuring never overwrites the player's world. `docs/development.md` says so.

12. **No release.** M14 plus world saving is not v0.3 (owner's decision). This milestone does no release work.

## Exit

Step 6 is done when:

- quitting and relaunching brings back the same creatures, drawn ones included, with their needs, home and knowledge;
- a short gap resumes exactly where the world stopped;
- a long gap applies ADR 0018 §19's catch-up: rested if the night passed, fed, asleep at home at night, and no per-creature events;
- restoring and carrying on gives the same result as an unbroken run, given the same later commands and time of day (checked headless, §8);
- a corrupt or incompatible save falls back to a fresh world with a logged warning, never a crash;
- `pnpm check` and `pnpm soak` pass with save and restore checks;
- a manual checklist entry is added and run by the owner;
- this ADR records the decisions and every departure from them.

## As built

PR 1 replaced the stale `CreatureInstance` schema with a strict `WorldSaveSchema` in `content-schema`: `schemaVersion` (`WORLD_SAVE_SCHEMA_VERSION`, 1), `savedAt` in ms since the epoch, `world` ID and version, `seed`, `tick`, `minutes`, `dayPhase`, the world `rng`, `nextCreature`, `introducedSpecies`, `species` (ID → exact version) and `creatures`. RNG state words are saved as signed 32-bit integers, as the generator holds them; the stream key is unsigned. Each creature entry mirrors `CreatureState` field for field, with action state and behavior memory left `unknown` for their owning code to validate. Because `content-schema` may not import the simulation, the schema repeats the simulation's types by shape, and the simulation checks at type level that the two agree (PR 2). `parseWorldSave` reports a save of another version as a single `unsupported_save_version` diagnostic and never migrates it.

PR 2 added `Simulation.save(savedAt)` and `Simulation.restore(save, { nowMs, minutes })`. Restore replaces the running world, keeping registered content, so drawn species registered at startup are kept. It restores the seed (the root stream is rebuilt from it), the world stream, the creature ID counter, introduced species, tick, `minutes` and `dayPhase`, then applies the present time of day as `set_time_of_day` does, so no false phase change is announced. After parsing, `checkSave` discards a save of another world or world version, or one whose creatures disagree with its `species` list or `nextCreature`. It drops creatures of a missing species or another major version, moves kept creatures to the registered version of their species, and prunes home, knowledge and used-structure entries naming missing placements. Behaviors prune their own memory through an optional `forgetPlacements` hook, which `core:feed` implements; a hook that throws loses that behavior's memory. The report lists what was dropped and pruned. Catch-up is a single private seam, `#catchUp(gapMs)`, left empty for PR 3. The simulation checks at type level that `CreatureState` and `RngState` are identical to the save schema's types.

PR 3 filled the catch-up seam. `runtime/catch-up.ts` holds the gap rules: a gap is capped at 12 hours, and a clock that went backwards or didn't move, or a gap under 2 minutes, is no gap. Custom day mode has no clock source yet; the seam notes that it must skip catch-up when it lands. The gap is taken to end at the present time of day and is split into the day phases it passed through. When catch-up applies, the engine moves the tick on by the gap, so every tick-based timer (the release grace, cooldowns in behavior memory, when places were last seen) counts the time away. It sets the day phase to the present one, so no phase change is announced. For each creature it drops the running action, its last result and any pending phase reaction, and sets its first decision after a random delay of up to 30 s. Then it calls each behavior's optional `catchUp(observation, gap, rng)` hook, which may set needs the behavior declares and ask for an action already under way at a placement's spot. A creature no hook places is put awake at a random reachable point in its home's region, or in its own region. The engine's draws and each hook's come from streams forked off the creature's own and salted with the tick after the jump, so a later restore draws afresh. Every event emitted during catch-up is discarded. `core:feed` sets hunger below `actAt`. `core:rest` lowers tiredness at the asleep rate through the sleeping phase and raises it at the awake rate otherwise, resetting it to 0 when a sleeping phase ended during the gap (the ADR 0018 §19 note). In the sleeping phase it resumes `core:sleep` already asleep: at home, else at the nearest known shelter, which then becomes home, else where the creature stands. `core:sleep` accepts that start only during catch-up (`ActionContext.catchingUp`) and, at a shelter, only where the creature already stands at its spot. A hook that throws, a need it may not set, or an action that fails to start loses only that effect and is listed in `RestoreReport.catchUp.failures`. Restore also checks each saved running action: one whose action is no longer registered, or whose state fails or throws in the action's optional `checkState`, is dropped and listed in `droppedActions`, and the creature decides afresh. The four core actions implement the check, and eat and sleep also check that their placement still exists.

PR 4 added two request commands to the worker protocol, now version 10. `save` carries `savedAt` (wall-clock milliseconds since the epoch, a non-negative whole number, as the schema requires) and is answered by `saved` with the save as JSON text, serialized in the worker so the main thread can store it as is. `restore` carries that text back, untrusted, with the wall-clock time and the present time of day. The worker checks both numbers, parses the text, checks it with `parseWorldSave` and restores it. It answers `restored` with the engine's restore report, or `rejected` with `invalid_save_json`, the schema's diagnostics, `save_world_mismatch` or `save_inconsistent`, leaving the world as it was so the app starts fresh. Both commands queue like the others and apply between ticks, while paused too, so a save sent after a spawn includes the new creature. After a restore the host restarts its clock, so time owed to the replaced world never ticks in a burst, and a paused host sends a snapshot of the restored world at once. `ActionEvent` moved to `creatures/action-event.ts` so the protocol can name the restore report without a dependency cycle.

PR 5 added `world.rs` in the Tauri app with two commands, `load_world` and `save_world`, which keep the save as raw text in `world.json` in the data directory (or `LIVING_DIORAMA_DEV_DATA_DIR` in development builds). A save writes `world.json.tmp` and flushes it to disk, moves the old `world.json` to `world.prev.json` only if it passes the same read checks as a load (so a corrupt save never replaces a good backup), then renames the new file into place, one save at a time, at most 16 MiB. A load falls back to `world.prev.json` when `world.json` is missing, too large, not UTF-8 or not valid JSON, and logs why. When either file exists but can't be read, `load_world` returns an error instead of reporting no save (changed in PR 6). The atomic write, size-limited read and data-folder helpers moved to a shared `storage.rs`, and `desktop-integration` gained `WorldStore` with Tauri and in-memory versions.

PR 6 wired saving into the desktop app. `SimulationClient` gained `save()`, `restore(json)` and `spawnStartingCreatures()`, and no longer spawns the starting creatures on `ready`. `world-saving.ts` opens the world once the library has registered its species. It loads the text from `WorldStore` and sends `restore` with `Date.now()` and the present time of day. On `restored` it keeps the world and logs the report, as a warning when anything was dropped, pruned or caught up. On `rejected`, with nothing saved or when the load fails, it logs why and spawns the starting creatures, never before the reply. When the load fails, nothing is saved for the rest of the session — no save after startup, no autosave, no save on quit — so a save that is there but can't be read for now, such as a file another program holds, is never replaced. The Studio reaches the library only after that, so a creature released during startup can't be replaced by the restore. The world is saved once open, then every 60 seconds, after each successful spawn or despawn (release, + and −, delete) and on quit, before `shutdown`. Saves run one after another through a promise queue, so an older save never lands after a newer one, and a save asked for while another waits shares it. Nothing is saved before the world is open, so quitting during startup never overwrites the save with an empty world. With the creature-count override set the app neither loads nor saves. The quit timeout rose to 3 seconds. Measured in a development build, a save takes 30–110 ms in the worker, mostly waiting for the next tick, plus about 5 ms to store 3–9 KB. Saving on quit took about 100 ms with the strip hidden for seven minutes. On `restored` the renderer's snapshot interpolation and debug stats restart at the next snapshot, so an older restored tick or catch-up's jump neither freezes creatures nor reads as a tick rate. Development builds expose `livingDiorama.world.reset()`, which takes every creature out, spawns the starting ones and saves. It keeps the seed, tick and ID counter.

PR 7 put saving into the headless tools. `pnpm sim --save <file>` writes the world as the run leaves it, and `--load <file>` starts from a save instead of a fresh world, with `--gap <minutes>` of wall-clock time away (default 0, an exact resume), so a gap of 2 minutes or more is caught up as in the app. The tick rate is not in the save, and tick-based timers mean simulated time only at the rate they were counted at, so both flags run at the app's 10 Hz only and refuse another `--hz`; adding the rate to the save would have changed the schema and the engine for the sake of a tool. `pnpm soak` saves and restores each run four times, at ticks drawn from its seed. Every save goes through JSON text and `parseWorldSave`, as the app's do, into a fresh world of another seed, and must restore with nothing dropped or pruned. After a restore without a gap, the world from before the save runs on beside the restored one for 10 simulated minutes; the two must make the same decisions and emit the same events every tick and end in the same save and snapshot. The comparison leaves out the debug snapshot: its routes, the only debug data the save doesn't cover, come from a cache of the last path walked that a restore clears. One restore per run comes after a gap of 2 to 16 hours, and the step after it must show the catch-up rules: the tick moved on by the capped gap, no phase change and no per-creature events, every creature fed, asleep at home in the night and awake by day, and rested if the night ended during the gap. `docs/development.md` gained the save's place in the dev data folder, the count override's skip, the reset hook, the tool flags and a manual checklist for world saving.

## Consequences

- Creatures and their individual state survive a relaunch, so behavior that shows over hours (sleep, homes, knowledge) is no longer lost each launch.
- Saves are written whole. That is cheap at one world and about 20 creatures, but a larger world or a world with edits may need incremental saving; step 7 revisits storage.
- Any change to `CreatureState` or the save format makes old saves fail validation and start fresh. That is accepted until backward compatibility is required.
- Catch-up stays content-driven: a new need's behavior adds a `catchUp` hook rather than engine code.
