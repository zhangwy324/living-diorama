# ADR 0015: Creation Studio

- **Status:** Accepted
- **Date:** 2026-10-27
- **Context:** Roadmap M11. The player draws a creature and releases it into the world. The strip never takes focus (ADR 0008 §6), so it can't take keyboard input such as undo shortcuts or a name, and the Studio needs a window of its own. The simulation worker and the species library (ADR 0014) live in the strip's window. M11 ships as four PRs: **1** this ADR and an editor performance spike; **2** the Studio window, the editor and the window channel; **3** the live preview, name and size, hints and the limits query; **4** release and the list of the player's creatures. Decisions for all four are recorded here; each PR updates this ADR if it has to deviate.

**Amended by [ADR 0017](0017-hollow-bodies-and-fill.md)** (M13): the hints check runs on the real shapes, holes included (§7, PR 1); the editor paints into a bitmap, with undo by changed-pixel patches rather than replaying strokes, and draws the live stroke a run at a time (§9, §11, PR 2, implemented; see the amendments there); and a fill tool joins the pen and the eraser on the toolbar (§10 there, PR 3, implemented), with a fill as a step of its own for the preview's rebuild, undo and redo, like a stroke.

## Decisions

### The window (PR 2)

1. **A separate, normal window.** Label `studio`: framed, resizable, focusable, with a taskbar entry and an Alt+Tab entry. Rust creates it on demand with `WebviewWindowBuilder` when the controls overlay or the tray asks for it (an `open_studio` command and a tray menu item). There is one at a time: opening it again shows and focuses the existing window. Closing it destroys it, which frees its WebGL context (§7), and never touches the simulation. The strip keeps every ADR 0008 behaviour, non-focusable included. PR 2 found that `WS_EX_NOACTIVATE` holds against other apps but not against the Studio: the strip's webview shares the Studio's input queue, so a click in the strip activated it (`WA_CLICKACTIVE`), and closing the Studio activated the strip too. `WM_MOUSEACTIVATE` never reaches the strip's window, so the strip hands activation back instead: whenever it is activated, it activates the window it took activation from, or, if that is gone, the topmost ordinary window of another app. Clicks and drags still reach the strip. Expanded mode (issue #30) is a separate question and out of scope.

2. **A second Vite entry.** `apps/desktop` builds two pages, `index.html` (the strip) and `studio.html` (the Studio), as a multi-page Vite build, sharing the workspace packages. The Studio page never starts a simulation worker.

3. **Its own capability file.** `capabilities/studio.json` grants the `studio` window only what it uses: listening and emitting to a target (`core:event:allow-listen`, `allow-unlisten`, `allow-emit-to`), the window calls behind the close dialog (§10), and the log. The strip's `default.json` stays scoped to `main`, and gains `allow-emit-to` for the channel's replies (it has only listen and unlisten today).

### Talking to the world (PRs 2–4)

4. **The world stays in the strip's window.** The worker, the registries and the species library stay in `main`. The Studio holds no world state of its own, only its drawing and the latest library snapshot.

5. **A typed request/response channel in `desktop-integration`.** The only package that imports `@tauri-apps/api` (ADR 0008 §1) gets a small channel over targeted Tauri events:
   - the Studio sends `studio-request` with `emitTo("main", …)`: `{ requestId, request }`, where `request` is one of release (save the drawing and add a creature), add a creature, remove a creature, delete a species, and check the limits for a size class (§8);
   - `main` answers with `emitTo("studio", "studio-response", { requestId, result | error })`;
   - `main` pushes `library-changed` with a snapshot of the library to `studio` whenever it changes. The Studio asks for one when it opens (a `snapshot` request), because a push sent before its listener exists is lost.

   Each side listens with its own label as the target (`listen(event, handler, { target: label })`). `listen` defaults to any target, which would also deliver events emitted to the other window. The Studio's requests time out after a few seconds, so a reloading or busy strip shows an error rather than a stuck button. Both ends have a no-op or in-memory implementation for tests, like `DesktopShell`.

   Payloads are JSON. A release carries the drawing (at most a few megabytes for a very long one, under the 16 MB file limit of ADR 0014) and the PNG bytes as a number array, which is fine for a 256 px image. Images in the snapshot are not `blob:` URLs: those belong to the strip's document. The Studio loads a species' image itself with `load_library_image` when it needs to show one.

6. **The Studio ignores shell broadcasts.** Rust sends `quit-requested`, `paused-changed` and `expanded-changed` with `app.emit`, which reaches every window, and exits on the first `quit_ready`. So:
   - the Studio page never creates a `DesktopShell` and never subscribes to these events, so it can't answer `quit-requested`;
   - `quit_ready` also takes the calling window and ignores any caller but `main`, since app commands are callable from every window regardless of capabilities;
   - shell events meant for the strip move to `emit_to("main", …)`, so a listener that names the Studio's label doesn't receive them. PR 2 found that a listener with no target (`listen`'s default) still hears events emitted to any window, so this holds because the Studio never subscribes to them and every channel listener names its own label.

   **The library commands are open to every window too** (recorded in M12). For the same reason as `quit_ready`, the Studio can call `list_library`, `load_library_drawing`, `load_library_image`, `save_library_entry` and `delete_library_entry`, although it uses only `load_library_image`, and its capability file can't take the others away. This is accepted. The app loads only its own bundled pages, so nothing but the app's code can call them, and Rust still checks every ID and file size (ADR 0014 §4). If a window ever loads remote content or third-party plugins, revisit this: check the caller's label as `quit_ready` does, or put the commands behind permissions.

   Quitting closes the Studio with the app, and a drawing that wasn't released is lost. This is a known gap, accepted for M11: the close dialog (§10) only covers closing the Studio itself, and saving drafts closes the gap later.

### Preview and limits (PR 3)

7. **The live preview uses the renderer's body code.** `renderer`'s `index.ts` exports `buildBody` and `readImage` (ADR 0011 §1). The Studio runs its own small three.js scene, lit like the diorama, with the body turning slowly and rebuilt from the rasterised drawing (§9) a short while after each stroke ends. The second WebGL context exists only while the Studio is open.

   PR 3 put the scene in `renderer` rather than the app, so the app keeps no three.js code of its own and the preview shares the diorama's lights: `index.ts` exports `createBodyPreview` (which uses `buildBody`) and `checkBody` instead of `buildBody` and `readImage`. The preview is built from the drawing's pixels at one pixel per unit, which `rasterize` encodes, so it matches the world's body. Details:
   - **When.** 200 ms after the strokes last changed (a stroke ends, undo, redo, clear), never during a stroke, and the preview neither turns nor renders while a stroke is drawn. Otherwise it renders at about 30 fps. In the dev app (WebView2, 100 Hz display, device pixel ratio 1), synthetic mouse strokes of 600 moves kept every frame at full rate with the preview showing a body (mean 10.0, p95 10.1, max 10.2 ms), as did the idle Studio with the body turning. A rebuild of a 28-stroke drawing takes about 34 ms on the Studio's main thread (pixels 0.8, `checkBody` 8.7, body and tint 24 ms), once per stroke end, which shows as one 30 ms frame.
   - **Size.** A new drawing starts at medium, the mossling's size, rather than the roadmap's small: medium is the size the built-in world is made for, so a first drawing starts without a size hint. The body is the chosen size class's height, over a ground grid of 25 cm squares. The view grows with the square root of the height, so a large body looks bigger than a tiny one while every size stays visible, and wide or tall drawings get more room so a turning body never leaves the view.
   - **Hints.** `checkBody` measures the same solid shapes the body is built from (`solidShapes`: opaque at `ALPHA_THRESHOLD`, 4-connected, specks left out), holes included. _Amended by [ADR 0017](0017-hollow-bodies-and-fill.md) §1:_ PR 3 measured the opaque mask with holes filled, as bodies were built then; now a ring's thin wall is thin and a shape inside a hole is loose. A part is _thin_ where a disc 3% of the drawing's height across doesn't fit inside it (7 px for a drawing 230 px tall), by a Euclidean morphological opening; thin areas of a few pixels (corners, jagged edges) are ignored. Because the measure follows the drawing's height, a lone line is not thin: its body is as deep as the line is tall. _Separate shapes_ are those solid shapes. The preview tints thin parts orange and every shape but the largest blue, with a see-through layer over the body that shares its geometry and texture coordinates, so the tint covers faces and sides alike.

8. **A read-only limits query.** A new worker command, `check_limits` with a `requestId`, a size class and the capabilities drawn species use (ADR 0014 §11; a navigation profile is size class plus capabilities, ADR 0012), answered by `limits` with the profile's limits as `Diagnostic[]` (ADR 0013 §4). It registers nothing. A known profile answers from the world state; a new one builds its navigation and checks it (about 30 ms in the worker) and keeps the result, so switching back and forth in the size picker is instant and a later registration of that profile can reuse it. Errors for the profile (e.g. `no_spawn_point`) come back as diagnostics too, so the Studio can say the size can't be released. `PROTOCOL_VERSION` stays 4 if v4 is still unreleased then, else it goes to 5. The Studio turns limit codes into the player's words.

   As built in PR 3: v4 is still unreleased (v0.1.0 shipped v2), so `PROTOCOL_VERSION` stays 4. Each limit is a `Limit`, a `Diagnostic` with the structure it is about, if any (`structure: { id, name }`, from the diagnostic's path and the structure definition's name), so the Studio can say "too big to cross the wooden bridge" without parsing messages; `species_registered` carries the same. A profile whose check fails keeps its errors too. An unknown size class or capability is misuse and answered with `rejected`. The strip answers the Studio's `limits` request once the world is ready, with `DRAWN_SPECIES_DEFAULTS`' capabilities, and the Studio asks once per size class while it is open. Each code has a short line (`portal_unusable` names the structure; `disconnected_region`, `no_walkable_area`, `spawn_not_walkable` and `no_spawn_point` have their own), and any other code a general one; the same line is said once.

   _Amended by [ADR 0020](0020-body-plans-swimming-and-live-edits.md) §12 (planned, M16 PR 5):_ the Studio asks for limits with the capabilities the player chose in the confirm panel (land movement, swimming or both), not `DRAWN_SPECIES_DEFAULTS`' fixed set. The land gait doesn't change them.

### The drawing (PRs 2 and 4)

9. **Strokes on a square 256-unit canvas, drawn as round lines through their points** (perfect-freehand outlines until the amendment below). The canvas is 256 × 256 units, the body image's size (ADR 0011 §1), shown scaled up to fit the window. Strokes keep the ADR 0014 format unchanged: tool (`pen` or `eraser`), colour, width at full pressure and flat `[x, y, pressure, …]` points in canvas units.

   A stroke is drawn by turning its points and pressures into an outline polygon with [perfect-freehand](https://github.com/steveruizok/perfect-freehand) (MIT, 1.2.x) and filling it as a `Path2D`: a pen stroke with its colour, an eraser stroke with `destination-out`. The options are fixed: `size` is half the stroke's width and `thinning` is 1, so the stroke is `width × pressure` wide, as ADR 0014 defines; `simulatePressure` is off, since the pressure is in the points (§11); a finished stroke is drawn with `last: true`. One function does this for the editor and for `rasterize`, which moves out of `dev-library.ts` into a module both use (the console hook keeps using it), so the 256 px PNG the body is built from matches what the player saw. Species saved before this change keep their stored PNG; only the sample drawing renders slightly differently from now on.

   **Amendment (M13, issue #59): the canvas draws the line itself.** Wide strokes drawn with a mouse had spikes on their edges. Reproduced with mouse-like input (whole CSS pixels of the scaled canvas, uneven spacing, sudden changes of speed), the spikes were just as bad with the pressure fixed at 1, so the derived pressure (§11) wasn't their cause. perfect-freehand offsets each side of the outline along a direction estimated from neighbouring points. Where a slow or trembling mouse leaves points a fraction of a unit apart, that direction swings from point to point, and at a radius of 20 units the outline zigzags back and forth across the edge. Less `smoothing` made it worse and dropping close points hid it, but any estimated direction can fold the same way.

   A stroke is now every point within `width × pressure / 2` of the line through its points, which is what ADR 0014 means by the width. The canvas's own `stroke()` draws it, with round caps and joins and the native anti-aliasing. An even stroke (every mouse stroke now, §11) is one line through its points. A pen's varying pressure is drawn in steps of 1/64: the stroke is split into runs of one width where the pressure, changing evenly between two points, reaches the next step, and each width is one path. A step is left only once the pressure reaches the next one, so noise smaller than a step adds no runs, and the width changes at most once per canvas unit along a segment, so wild pressure can't make thousands of them. A lone point is a filled circle, since a canvas may draw nothing for a line of no length. There is no `last` any more: the live stroke is drawn with the same call it is baked with, so it doesn't change when it ends. perfect-freehand's smoothing of the points (`streamline`) is gone too, so an edge follows the mouse's pixel steps (under half a canvas unit at 100% scaling). The dependency is removed.

   Measured in headless Edge on a 1400 px canvas: a 2000-point even stroke takes about 0.6 ms (perfect-freehand: 0.4 ms). A 2000-point pen stroke whose pressure also wobbles by ±0.02 at every sample takes about 12 ms, and one whose pressure jumps by ±0.3 at every sample about 27 ms. So a long pen stroke with noisy pressure can now take more than a frame to redraw while it is drawn, since the whole live stroke is redrawn every frame; mouse strokes are unaffected. Drawing the live stroke incrementally was left to the bitmap editor (M13 PR 2; done, see the next amendment). Library entries keep their stored PNG; redrawing their strokes (undo, the sample drawing) gives the new edges.

   **Amendment (M13, issue #73): the image is the drawing, and the live stroke is drawn a run at a time.** The editor's drawing is now the 256 px image itself (ADR 0014 §5 amendment), shown scaled up smoothly, so the player sees exactly the pixels the body is built from: slightly softer than drawing at device resolution, never blocky. `rasterize` and `drawingPixels` are gone: release encodes the editor's image and the preview reads its pixels. The development samples, drawn by code, paint their strokes once into an image (`paintStrokes`, now `paintHistory`, which also replays fills), as a player's strokes are painted.

   While a stroke is drawn, its runs (`strokeRuns`) are drawn in pieces. Every run but the last is finished, since later points only extend the last run or start new ones, so each finished run is drawn once into a working copy of the image; each frame copies that and draws only the open run on top, at 256 px, then scales the result to the canvas. When the stroke ends it is painted into the image whole with `drawStroke`, so what is kept is exactly what `drawStroke` draws. The live view can differ from it only in the soft edge pixels where two runs of the same width overlap, which one path blends once and two paths twice; nothing of it is kept.

   Measured in headless Edge, with the 256 px image scaled to a 1400 px canvas and each frame closed by a one-pixel read so the GPU work is counted (that read alone costs about 4.5 ms, which every number here includes): for a 2000-point pen stroke whose pressure wobbles by ±0.02 at each sample (577 runs), a frame at 2000 points took 10.5 ms before and takes 4.5 ms now; with pressure jumping by ±0.3 (2102 runs), 31.3 ms before and 4.5 ms now, and 4.5 ms for an even stroke (6.5 ms before). The new frame no longer grows with the stroke's length or noise: over the whole stroke, frames averaged 4.5–4.9 ms against 4.8–16.3 ms before. Splitting the stroke into runs each frame takes 0.1 ms at 2000 points. Painting the finished stroke into the image and recording its pixels for undo takes 1.6–7.6 ms once, at the end.

10. **Closing with an unreleased drawing asks first.** Closing the window while the canvas has strokes that weren't released shows a dialog: **Discard** closes, **Save draft** is shown but disabled ("coming later"), **Cancel** keeps the Studio open. An empty or released drawing closes without asking.

11. **The editor is a plain `<canvas>`, not React Konva.** The roadmap proposed React Konva; the spike below showed it doesn't fit this editor. React renders the toolbar and panels only. The canvas is driven imperatively:
    - **Finished strokes are baked into a bitmap.** A frame with a live stroke draws the bitmap, then the live stroke's round-capped lines (§9), so only the live stroke is redrawn. A live eraser stroke draws its lines with `destination-out` over the bitmap, so the result is exact while erasing. When a stroke ends it is baked in. (Amended in M13, issue #73: the bitmap is the 256 px drawing itself, and the live stroke is drawn a run at a time; see the §9 amendments.)
    - **Undo and redo replay the stroke list.** The bitmap is rebuilt from the strokes left (undo) or drawn one stroke further (redo). The stroke list is the only state. **Amendment (M13, issue #73):** the image is the state, and undo and redo put pixels back instead of replaying strokes. Each step keeps the pixels it changed, before and after, cut to the smallest rectangle around them (a step that changed none keeps none), and the record (ADR 0014 §5) it replaced. A typical stroke costs a few tens of kilobytes, a Clear 512 KB. Undo keeps at most 32 MB of pixels, about a thousand ordinary strokes and at least 64 whole-canvas changes, and forgets the oldest steps beyond that; the newest step is always kept. Drawing after an undo drops the undone steps. Release now waits for the preview's check of the image and needs it to find a body (`checkBody`), so a drawing erased back to nothing, or one of faint pixels only, can't be released as an empty image; closing asks first only when some pixel is visible.
    - **Live points are not React state.** Pointer handlers append to the live stroke and request a frame.
    - **Every sample counts.** Moves read `getCoalescedEvents()`, so a pen's samples between frames aren't lost. The context is created with `desynchronized: true` for lower latency if PR 2 confirms that it helps and renders correctly in WebView2; otherwise it is left off. PR 2 found that WebView2 takes it (input stops waiting for frames) but then shows the canvas's transparent pixels as black rather than the page behind them, so it is left off.
    - **Pressure.** A pen (`pointerType` `pen`) stores the pressure it reports. A mouse reports a constant 0.5 and touch varies by device, so for every other pointer the Studio stores a pressure derived from speed instead: it eases towards a target that falls from 1 when the pointer moves slowly to a floor of about 0.35 when it moves fast, so quick flicks taper like a brush. PR 2 tunes the constants. Because the derived pressure is stored, replaying a stroke never needs to know which pointer drew it. **Amendment (M13, issue #59):** every pointer other than a pen now stores pressure 1, so a mouse stroke is the brush's width all along. The width from speed changed with every jerk of the hand, which looked unnatural on wide brushes, and the brush sizes are already the player's way to choose a width. It wasn't the cause of the spikes (§9), only made them look worse. Strokes saved with a derived pressure still draw as stored.
    - **The backing store follows `devicePixelRatio`.** The guide ("facing right, feet on this line") is a separate element over the canvas, so it is never part of the drawing.

### Release and My creatures (PR 4)

12. **Release and the list, as built.** The channel gains `release`, `addCreature`, `removeCreature` and `deleteSpecies`; the strip answers them with the species library (ADR 0014):
    - **Release** saves the drawing (`library.save`, which registers and stores) and adds one creature. The button is disabled while nothing is drawn or the name is empty after trimming, and shows it is busy while waiting, so there is one release at a time; the canvas can't be drawn on meanwhile. On success the Studio says "<name> is off into the world!" for a few seconds, and starts over: an empty canvas with no undo history, the next "Creature N" and medium. On failure the drawing stays and the error is shown. _Amended (issue #48):_ the name starts as a playful two-part suggestion (such as "Mossy Pebble") that skips names already in the library, kept until a release or the reroll button beside the field picks another, instead of "Creature N".
    - **A retry never saves twice.** The Studio makes the species' UUID (`releaseId`) when the player first presses Release and keeps it while the drawing, name and size stay the same, so a release whose answer timed out is sent again with the same ID. The strip keeps each release's promise by ID, so a repeat, during or after the first, gets the first's answer; a failed one is forgotten so it can be tried again. If the strip reloaded in between, a species already stored under that ID is not saved again, only given a creature (the reloaded world has none). The 5 s channel timeout is unchanged; a release in the dev app answers in about 0.2 s.
    - **The cap.** The strip refuses a release into a full world before saving anything, with the worker's words ("The world is full (20 creatures). Remove one to add another."), so the drawing stays; adding past the cap says the same. If the world fills between the check and the spawn, the species is kept and the Studio says it couldn't join yet.
    - **My creatures** is a collapsible panel beside the preview, drawn from the snapshot: picture, name, count in the world, + and − (disabled at 0; − takes out the newest), and delete after a confirmation that says how many leave the world. A species the world rejected is listed as unavailable with the reason, and can only be deleted. The snapshot carries each species' library UUID and count, and the world's total and cap; the strip pushes it when the library changes and when a snapshot's count per species changes. The Studio loads each picture with `load_library_image`, makes its own `blob:` URL and revokes it when the species leaves the list or the Studio closes.
    - **Manual checks** in `pnpm dev` use a separate library: development builds read `LIVING_DIORAMA_DEV_DATA_DIR` and keep `library/` there.

## Spike: React Konva or a plain canvas

A throwaway harness (not committed) drew ADR 0014 strokes, each segment at `width × pressure`, on a 256-unit canvas shown at 640 CSS px (device pixel ratio 1.5), with `react-konva` 19.3.2, `konva` 10.9.0 and React 19.3.1. It ran in Microsoft Edge (WebView2's engine) with the GPU, driven by synthetic pen events with varying pressure through `puppeteer-core`, on a 100 Hz display, where 10 ms is a full-rate frame. It seeded 50 strokes of 750 points, drew a new stroke at 2 pointer moves per frame, and undid and redid a stroke. Undo times include waiting for the next frame (at least 20 ms).

| Editor (50 × 750)                                             | Frame while drawing, mean / p95 | JS per frame | Undo    |
| ------------------------------------------------------------- | ------------------------------- | ------------ | ------- |
| Plain canvas: finished strokes kept, new segments drawn       | 10 / 10 ms                      | 0.05 ms      | ~38 ms  |
| Konva `Shape` per stroke, custom `sceneFunc` for pressure     | 32 / 40 ms                      | 0.2 ms       | ~53 ms  |
| The same, with the live stroke in React state                 | 33 / 40 ms                      | 5.5 ms       | ~46 ms  |
| Konva `Line` per stroke (one `strokeWidth`, pressure ignored) | 31 / 40 ms                      | 8.1 ms       | ~60 ms  |
| Konva `Line` per segment (a width each)                       | 302 / 430 ms                    | 258 ms       | ~240 ms |
| Konva `Shape` per stroke, finished strokes cached to a bitmap | 10 / 10 ms                      | 0.3 ms       | ~38 ms  |

With 10 strokes of 500 points every variant tried kept full rate. With 50 × 1000, uncached Konva fell to 42 ms frames, while the plain canvas and cached Konva stayed at 10 ms.

What it shows:

- **Konva redraws the whole layer every frame,** replaying every stroke, so each new stroke gets slower as the drawing grows. The cost is in rasterising, not in JavaScript or React.
- **Pressure needs custom drawing in Konva.** A `Line` has one `strokeWidth`, a `Line` per segment is unusable, and a `Shape` with its own `sceneFunc` is plain canvas code inside Konva.
- **Live points in React state cost 5–16 ms of JavaScript per frame.** They stay out of React whatever draws them.
- **Konva is fast only with the finished strokes cached to a bitmap,** which is what the plain canvas does by itself. Konva then contributes no shapes, hit testing or transforms that the editor uses.

So a plain canvas, the fallback roadmap risk R1 named. The spike drew strokes segment by segment; perfect-freehand was chosen afterwards for the look: smooth, tapered, pressure-shaped strokes from the same points, in a small library without dependencies, the one Excalidraw uses for freehand drawing. With it the live stroke's whole outline is rebuilt each frame rather than only its new segments; PR 2 checks that this stays well inside a frame for long strokes. It does: in the app (WebView2, 100 Hz display, device pixel ratio 1, canvas 640 px), a synthetic pen stroke growing to 2000 points at one move per frame kept every frame at 10 ms (mean 10.0, p95 10.1, max 10.3 ms), and rebuilding and filling a 2000-point live stroke takes about 1.1 ms, of which perfect-freehand's outline is 0.2 ms.

## Consequences

- The app has a second window and a second page. The manual checks in `docs/development.md` gain a Studio section with PR 2: focus, one instance, closing, scaling and two monitors.
- `desktop-integration` grows the window channel and stays the only package that imports `@tauri-apps/api`. Rust's shell events go to `main` only.
- One new runtime dependency, `perfect-freehand`, for the Studio and `rasterize` (removed again by the §9 amendment). No scene-graph library: shapes, selection or transforms in later drawing releases would be a reason to look at one again, and the stroke format doesn't depend on the choice.
- The editor and `rasterize` share one stroke-drawing function, so the released image matches what the player saw.
- A drawing that isn't released is lost when the Studio closes (after asking) or, without asking, when the app quits. This is accepted for M11; saving drafts fixes it.
- A limits query for a new size class builds that profile's navigation, which stays in the worker even if nothing of that size is ever released, like a deleted species (ADR 0014 §9).
