# ADR 0021: Live prop editing

- **Status:** Accepted
- **Date:** 2026-10-29
- **Context:** Roadmap §3.2 step 7 paired drawing release 2 with live world edits. [ADR 0020](0020-body-plans-swimming-and-live-edits.md) built the first half as M16 and fixed M17's contracts in advance (§16–§21): edits to props and structures, a save that stores an edit list replayed onto the base world, and navigation rebuilt per touched region. When M17 started, the owner rescoped it on 2026-10-29. M17 now edits **props only** (add, remove, move, scale), **live** while creatures carry on, through **one pipeline** that rebuilds the whole derived world after each edit, and the **edited world itself is embedded in the save** instead of an edit list. Structures, terrain and region edits, and a library of user worlds come in later milestones (roadmap §3.2); this ADR keeps the door open for them without building them. The decisions below were agreed with the owner on 2026-10-29 and supersede ADR 0020 §16–§21. M17 lands as a series of PRs: **0** this ADR; **1** the edit ops, result and inverse in `content-schema`, and a measurement of the full rebuild's time (§1–§3, §10, §11); **2** the simulation: applying and validating an edit, the full rebuild, reconciling creatures, events, and the protocol and host messages (§1, §3, §5–§10); **3** the renderer: props (and overlays) rebuilt from new scene data, and a read-only prop picking API (§12); **4** persistence: the edited world in the save (§4); **5** tools: edits in `pnpm sim`, scenarios and random edits in the soak; **6** the app: a dev console hook and the in-strip editor, and the manual checklist (§12). PRs 1 and 3 come first, then 2, then 4 and 5, then 6. Each PR adds its own paragraph under "As built" below, recording what it built and where it departs from this ADR.

This ADR supersedes ADR 0020 §16–§21. How the Studio commits world edits stays as ADR 0020 settled it ("Contradictions resolved"): through the worker's one edit command, reached through the strip. It amends ADR 0019 §7 (a save of an edited world no longer needs the registry's world to match, §4) once PR 4 lands.

## Decisions

### The edit pipeline

1. **One edit pipeline, with a full rebuild.** An edit is a pure function from one `WorldDefinition` to the next. After applying it, the engine rebuilds everything derived from the world as if the world had just loaded: the world model, navigation for every profile and the scene data. It then reconciles the creatures with the new world (§6–§8). There is no per-region or dirty-rectangle rebuild; ADR 0020 §20's region rebuild is dropped. Terrain and region edits later add new ops to the same pipeline, not a new path. Every caller (the dev hook, `pnpm sim`, the in-strip editor, later the Studio and the agent bridge) reaches the world through the worker's one validated edit command, applied between ticks like every other command (ADR 0006 §11). Nothing else changes world content at run time.

2. **Edit ops are an extensible discriminated union.** M17 has `prop.add`, `prop.remove`, `prop.move` (position and rotation together) and `prop.scale` (uniform). Later ops (`terrain.*`, `region.*`) join the same union. A `prop.add` carries the new placement's ID. By default the engine generates it deterministically from a counter kept in the simulation state and saved with it; a caller may supply its own ID instead, which is rejected if already in use. A generated ID skips any ID already in use, including one a caller supplied earlier.

3. **Live.** The worker accepts an edit at any time and applies it between ticks, never in the middle of a step. The world is not paused. The editor shows a preview while dragging and commits only on release, so a drag costs one rebuild. **PR 1 measures the full rebuild's time on Woodland Hollow against the 100 ms tick.** If it does not fit comfortably, the work stops there and live editing against a background or incremental rebuild is decided again with the owner before PR 2.

### Persistence

4. **The edited world is embedded in the save.** Once a world has been edited, the save holds its derived `WorldDefinition`, and a restore builds the world from that, not from the registry's world. Such a save no longer needs the registry's world ID and version to match (amends ADR 0019 §7 for edited worlds). A library of user worlds comes in a later milestone. The edit log is session history for undo and redo only and is not saved. The save's `schemaVersion` goes up; no migration is written (AGENTS.md, backward compatibility).

### Props and creatures

5. **A prop sits on the ground.** On `prop.add` and `prop.move` the engine sets the prop's height to the ground's height at its new position. The `y` field stays in the schema until terrain edits arrive, when dropping it is decided.

6. **Every creature replans after an edit.** Each creature drops its current route and plans a new one on the rebuilt navigation.

7. **A covered creature is moved, never deleted.** When an edit leaves a creature off any walkable cell of its profile (a prop placed or moved onto it, grown over it), the engine moves it to the nearest walkable cell in the main walkable area (the largest connected piece) of its own region, or of the nearest region its profile can move in, and emits an event saying so. The edit is rejected only when no such cell exists.

8. **Removed and moved placements are cleaned up.** For a removed prop, home, knowledge and behavior memory that name it are pruned as a restore prunes them (ADR 0019 §7, the behaviors' `forgetPlacements`). An action that targets a moved or removed placement is interrupted through the existing `interrupted` path.

9. **Blocking an exit out of water is allowed, with a warning.** As in ADR 0020 §19, an edit that blocks one or more water→land exits applies, and the result warns and names each one: an authored exit by its connection ID, a derived bank as `{ waterRegion, landRegion }`, since banks have no IDs.

10. **Validate first; return the inverse.** The edit command has a dry-run `validate` that reports, without changing anything, whether the edit would be accepted, the edited prop's footprint (the cells it would occupy), the warnings and the water→land exits it would block. An applied edit returns its inverse edit, so undo is one more edit, and redo the inverse of that.

11. **Scale has no fixed range.** A scale must be greater than 0 and the scaled footprint must lie inside the world's bounds; the edit check (§7, §9) handles the rest. A minimum and maximum per prop type may come later.

### Editing tools

12. **A minimal editor in the strip, plus a dev hook and `pnpm sim`.** The in-strip editor selects a prop by clicking it, drags it on the ground, deletes it, adds one from a palette of the registered prop types, scales it with the mouse wheel, rotates it with a key, and has undo and redo. Development builds also get a console hook, and `pnpm sim` runs edit scripts. The renderer stays read-only: it offers picking and the drag preview, and the app sends edit commands to the worker.

13. **Records.** This ADR records M17, and ADR 0020's M17 section is marked superseded. The private design docs are updated in their own repository.

## Exit

M17 is done when:

- a prop can be added, removed, moved, rotated and scaled through one validated edit command;
- `validate` reports an edit's outcome, footprint, warnings and blocked exits as a dry run;
- edits apply live, between ticks, without pausing the world; the full rebuild's cost is recorded in PR 1's "As built";
- every applied edit returns its inverse;
- creatures covered by an edit are moved to a walkable cell, with an event;
- a removed placement is pruned from home, knowledge and behavior memory, and actions targeting a moved or removed placement are interrupted;
- an applied edit that blocks a water→land exit returns a warning naming the exits;
- every creature's route is replanned after an edit;
- an edited world survives quitting and relaunching;
- edits work from the dev hook, `pnpm sim` and the in-strip editor;
- `pnpm check` and the full `pnpm soak` pass, with random edit cycles that include comparing a save and restore;
- a manual checklist entry is added and run by the owner;
- this ADR records the decisions and every departure from them.

## As built

Each M17 PR adds its own paragraph here, in its own slot, so PRs landing in parallel don't conflict.

### PR 1: schema and rebuild timing

`content-schema` defines the edit contract in `edit.ts`. `WorldEditOpSchema` is a discriminated union on `op`: `prop.add` (`prop`, horizontal `position`, `rotationY` default 0, `scale` default 1, optional placement `id`, which the engine assigns when it is left out), `prop.remove` (`id`), `prop.move` (`id` with `position`, `rotationY` or both) and `prop.scale` (`id`, `scale`). A scale must be greater than 0 and has no upper bound. Positions carry no height, since the engine puts props on the ground (§5). A `WorldEdit` is `{ ops }` with at least one op, applied in order and all or nothing, so a compound change is one rebuild and one undo step, and its inverse is the ops' inverses in reverse order. `parseWorldEdit` checks only the shape, and an op without `op` gets its own message. Whether an edit fits its world (the placements exist, footprints stay inside the bounds, creatures can be relocated) is the simulation's to check. The engine answers with `WorldEditResult`, whose `edit` and `inverse` are `AppliedWorldEdit`s in which every `prop.add` names its placement, or, for a dry run, `WorldEditCheck`. Both carry `footprints` (centre and block radius × scale), `warnings`, `blockedExits` (a connection ID or a bank `{waterRegion, landRegion}`, with the navigation profiles that lose it) and `relocated` creatures. A rejection carries diagnostics whose paths point into the edit. An inverse is exact only up to the ground snap: undoing restores position, rotation and scale, but a placement authored off the ground comes back on it. `pnpm rebuild-time` measures the rebuild. On a Ryzen 7 9700X (warm, 30 runs, two invocations), `WorldState.create` for Woodland Hollow takes a median of 26 ms with one navigation profile (the mossling) and 80–83 ms with three (the soak's species). A realistic edit, which is `WorldState.create`, the lazily built pathfinder data the relocation and blocked-exit checks need (crossings, areas, bank crossings) and 20 route queries per profile, takes a median of 35 ms (max 42 ms) with one profile and 117–144 ms (max 122–203 ms) with three. That is over the 100 ms tick. Navigation costs about 26 ms per profile, mostly walkability mask building (`buildRegionMask`, `pointInPolygon`), while the world model and scene data take under 1 ms. Live editing against this cost is to be decided with the owner before PR 2 (§3).

### PR 1b: faster navigation building

The owner kept live editing with a full rebuild between ticks, so PR 1b makes navigation building faster without changing its output. The facts about each region's mask cells that don't depend on the creature (footprint coverage, surface height and steepest sampled slope, dry water cells, water overhead, other surfaces within a step or above, edge distance) are computed once per world model in `navigation/region-cells.ts` and shared by every navigation profile. Each profile's mask then only applies its own rules: slope limit, height, radius and swimming. Footprints are tested a line at a time: each line's edge crossings are computed once, with the same arithmetic as `pointInPolygon`. Props mark the cells around them instead of every prop being tested per cell. `raisedSurfaces` is cached per world model, and jump checks only test props near the jump. The caches are keyed by the `WorldModel` object, so a model is never changed once built (its doc comment says so, and its fields are `readonly`): an edit builds a new one. The output is bit-identical. A test compares masks (states and height bits), banks and raised surfaces with the old per-cell build, kept as an oracle in `tools/development`, on Woodland Hollow with the soak's species, the other fixtures and a fixture whose surfaces and props sit exactly on the epsilon, step, headroom and clearance boundaries. On the same machine, `WorldState.create` for Woodland Hollow now takes a median of 6 ms (max 11 ms) with one profile and 12.5 ms (max 16 ms) with three. A realistic edit takes a median of 12.5–12.7 ms (max 16.5–17.5 ms) with one profile and 51 ms (max 60 ms) with three, down from 35 ms and 117–144 ms. With three profiles most of what is left is the lazily built pathfinder data and the route queries, not mask building.

### PR 2: simulation

`WorldState.create` takes a registered world's ID or a `WorldDefinition`. `derive(definition)` builds a new world model, the navigation of every profile the world has (the species' and any added since), checked as at creation, and their pathfinders, and `replaceWorld` swaps them in and forgets profiles that failed before. A model is never changed. Applying an edit to a definition is a pure function in `world/edit.ts`: `assignPlacementIds` gives each `prop.add` without an ID `prop-<n>` from a counter in `WorldState`, skipping IDs the world uses or the edit names, and `applyWorldEdit` applies the ops in order, all or nothing. It rejects an unknown placement, an ID in use (in the world's one namespace of local IDs), an unregistered prop type, a scale not above 0, and a footprint (block radius × scale) reaching outside the bounds. It puts every added or moved prop on the terrain and returns the inverse. Undoing a remove adds the placement back last in the list, not where it was. A placement removed and added back under its ID in one edit counts as changed. `runtime/world-edit.ts` plans an edit against the running world without changing it, so `Simulation.validateEdit` is a plan thrown away. The plan rejects an edit that leaves a profile with no walkable spawn point (`edit_breaks_navigation`, so a swimmer's only water can't be filled). It moves each creature that stood on a walkable cell and no longer does to the nearest cell centre in the largest walkable area of its region, else of the nearest region its profile moves in. `no_relocation` is only a guard: a profile that passes the spawn check always has such a cell. Blocked exits compare each profile's navigation before and after: a water→land connection whose portal stops being usable, and a bank that has no jump left anywhere along it. A bank that keeps one jump isn't reported. Limits new to the rebuilt world (by code and place) are added as warnings. `Simulation.applyEdit` runs only between steps (`edit_during_step` otherwise), swaps the world in, emits `world_edited`, then reconciles creatures in creature order. An action is interrupted (`world_edited`, through `interrupted`) if its `target` was moved, scaled or removed (a turn alone changes neither footprint nor spots, so it interrupts nothing and keeps back-offs), its `checkState` now fails, or its creature is moved (`creature_relocated`). `core:sleep` now has a `target`; only `core:eat`'s did. Removed placements are pruned with `forgetMissingPlacements`, which a restore now uses too. Every action that carries on replans through a new optional `ActionProvider.replan` hook (`core:follow_path`, `core:eat` and `core:sleep` replan their remaining route to its last waypoint), and is interrupted if no route is left. An action without the hook is interrupted (`world_edited`), since it may keep a route the edit made stale (#195); `core:idle`, which keeps none, has a hook that returns true. Reconciling never throws: it runs after the swap, so every pack hook it calls is guarded, and one that throws (including `target`) ends that creature's action. A throw from `applyEdit` therefore comes from planning, before anything changed, and the host answers it, like one from `validateEdit`, with `rejected` (`edit_failed`). Reach failures (back-offs) are cleared for placements the edit moved or scaled, since they described where the placement stood, and kept for the rest, so a home that keeps failing stays failing. The worker protocol (version 14) adds `edit` and `validate_edit`, answered by `edited` (the result) or `rejected`, and `edit_checked`. An applied edit is followed by `world_changed` (scene data and every profile's navigation overlay) and, while paused, a snapshot. The generated-ID counter (`nextPropId`) and the edited definition aren't saved yet; PR 4 must save both, or IDs generated after a restore could repeat ones an undo still names. A save of an edited world still names the registry's world ID and version, so it restores into whatever world is loaded: after a relaunch that is the unedited one, and references to added placements are pruned. Woodland Hollow with 20 creatures (Ryzen 7 9700X): `applyEdit` takes a median of 10 ms (max 16 ms) with one profile and 40 ms (max 50 ms) with three, replanning included. `validateEdit` takes 6 ms and 13 ms.

### PR 3: renderer

The renderer replaces the world's props mid-session with `DioramaView.replaceProps(scene, navigation)`, keeping terrain, water and structures as first built. Walkability and the region graph are rebuilt from the new navigation overlay, and the debug labels' lines and the cue bubbles' prop pictures follow the new placements; a call overtaken by a later one changes none of them. Prop models are loaded once per URL and cached for the life of the view (`PropSet`). A replacement waits until every model it needs is ready, then swaps all props in one step, so no frame lacks them. A load that has not settled after 10 s is drawn as the fallback block, so it cannot hold up later replacements, and lists placed after it arrives draw the model. Replaced instanced meshes are disposed; models, their textures and the shared fallback block are freed when the view is disposed. For the editor (§12) the renderer stays read-only (`PropEditing`). `pickProp` and `pickGround` work from a pointer position. The terrain is hit through its heightfield (a walk along the ray refined by bisection, on the drawn triangles, about 4 µs a ray on a world the size of Woodland Hollow), and only props and structures are raycast as meshes. Props hidden by the terrain or a structure are not picked, and hits the layers' clipping planes cut away are skipped. `selectProp` rings a placement and follows it through replacements. `previewProp` draws a see-through copy of a placement (model asset ref, transform, block radius), only moving it while the model stays the same. `hideProp` hides the original while its preview is dragged, through replacements, and a hidden prop is never picked. The preview takes a model asset ref, not a prop type, so the app maps prop types to models for its palette.

### PR 4: persistence

The save (`schemaVersion` 4, no migration) still names its world as `world: { id, version }` and now also holds `nextPropId`. When the running world isn't the registered one, that is when its definition is not the registry's object because it was edited (an edit followed by its undo counts too) or built from a definition, `world.definition` holds the whole `WorldDefinition` as well, whose ID and version must be those named. An unedited world isn't embedded, so its save stays small and follows changes to the built-in world. On Woodland Hollow the embedded definition is about 103 KB: a save is 7 KB unedited and 110 KB edited with 3 mosslings, 42 KB and 144 KB with 20, far below the shell's 16 MB limit, and taking and serialising it takes about 1 ms. A restore picks its world with `worldOfSave`. An embedded world is untrusted: the schema checks its shape, `checkReferences` (new in `extension-api`, the per-entry half of `addEntries`) resolves its prop and structure types, surfaces and capabilities against what is registered, and the world is rebuilt (`derive`, from a copy of the save's definition) for every navigation profile the world has. A prop type that isn't registered, or a world that can't be built (or throws while building), discards the save with `save_world_invalid` followed by the reasons, with paths into the save, and the world carries on as it was, like any unusable save. **This amends ADR 0019 §7 for embedded worlds:** their world ID and version need not match a registered world. A save without a world still must name the registered world the running one is or was edited from, at its version (`save_world_mismatch` otherwise), and restores into that registered world, unedited, even when the running world was edited. A running world whose ID isn't registered (built from a definition) accepts only saves that hold their world, which its own saves always do. `checkSave` no longer compares worlds; it checks the save against the world `worldOfSave` chose, so pruning (home, knowledge, used structures, behaviour memory) and the running actions' `checkState` work against the restored world, added placements included. The restore swaps the rebuilt world in only once the save has passed every check, and restores `nextPropId`, so IDs generated after a relaunch never repeat ones an undo or redo still names. When a restore changes the world's content, the host sends `world_changed` after `restored` (protocol 15), and the app redraws the props with `replaceProps`. The app saves on every `world_changed` (the existing save queue merges saves that pile up), so a crash right after an edit loses at most that edit. After the startup restore of an edited world, that queues a second save behind the one opening the world makes, which is harmless. The Rust shell is unchanged: it stores the save as text. The renderer keeps the terrain, water and structures it first built, which is right while only props can be edited; a save whose world differs in more than props is restored correctly by the simulation but drawn with the registered terrain until terrain edits come. The dev console's world reset keeps edits, since it only replaces the creatures.

### PR 5: tools

`tools/development` runs edits headless through one path: `runWithInvariants` takes an `edits` source, asked between steps for the edits to apply before the next, and applies each with `Simulation.applyEdit`. An undo request applies the inverse of the last edit applied and not undone; a refused undo keeps the history. Each edit is timed, every creature is checked at once as after a tick (finite, on a walkable cell of its own profile, on its region's surface, in bounds), and the long-run checks read the world model and navigation afresh, since an edit replaces both. `pnpm sim --edits <file>` reads a JSON array of `{ tick, edit }` or `{ tick, undo: true }` (`tick` counts steps from the run's start; edits go through `parseWorldEdit`), prints each result and writes it to the NDJSON without its time, so runs with the same script are the same. `world-edit-scenarios.test.ts` covers a prop dropped on a creature, the food a creature heads for and the home it sleeps at removed, the pond's shore exit blocked (a warning, and the newts still leave the water), a prop scaled over a walker's route (it replans to the same goal), the bridge's west end blocked (no failed path or stuck creature), and 60 random edits in 30 s, which give the same world on every run. `pnpm soak` makes 24 random prop edit requests per run (`--edits`) at steps drawn from its seed, about one in five an undo: adds, adds where a creature stands, removes, moves, scales and turns, some with two or three ops. Footprints keep 1.5 m from portals, the bridge, spawn points and the edge, so the bridge every mossling must cross stays open. The replan after an edit (`#reconcile`) plans without emitting `path_failed`: a walk whose goal the edit covered or cut off is interrupted (`world_edited`), so every `path_failed` in a run is a navigation fault again. The meal check decides afresh after each edit which creatures can reach food, since an edit may remove a swimmer's only reachable bush or cut a creature off on the summit (`disconnected_region`); a creature's clock between meals stops while it has no food in reach. Edits due on the step after a restore with catch-up wait a step, so the catch-up check sees the world as catch-up left it. While an unbroken twin runs beside a restored world, each edit applies to both and must answer the same. With PR 4's saves, a restore after edits starts from a fresh world of the unedited built-in world, as after a relaunch, and must bring back the edited definition and `nextPropId` exactly as saved, then, without a gap, carry on tick by tick as the unbroken run. The full soak (32 seeds, 16 jobs, Ryzen 7 9700X) passed in 176 s, against 158 s without edits, with 122 of its 128 restores of an edited world: 759 edits applied (170 undos), 9 undos refused with nothing left to undo, 119 creatures relocated, not one `path_failed`, 7 creatures cut off from food and 14 `disconnected_region` warnings, with `applyEdit` at a median of 43 ms (p95 112 ms, max 216 ms) with every core busy. No water-exit warning came up: Woodland Hollow's river is left by long banks, and one prop never takes all of a bank's jumps, so the pond scenario covers the warning. `pnpm rebuild-time` now also times `validateEdit` and `applyEdit` (an edit, then its undo) in a running world of 20 creatures: on the same machine, idle, a median of 6.3 ms and 10.1 ms (max 14 ms) with one profile, and 14.3 ms and 24 ms (max 30 ms) with three.

### PR 6: app

The app's `SimulationClient` gains `edit` and `validateEdit`, which resolve with the worker's `WorldEditResult` or `WorldEditCheck`, a `rejected` answer folded into the same failed shape. `EditHistory` (`edit-history.ts`) keeps the session's undo and redo stacks (at most 100 steps): an applied edit pushes its edit and inverse, undo sends the inverse and redo the inverse of that, all queued one at a time, so an undo asked while an edit is in flight undoes that edit. A refused undo or redo keeps its step, so it can be tried again. The history is forgotten on every restore (`onRestored`) and on the dev hook's `world.reset()`, and an edit in flight then adds no step. The dev console hook (`livingDiorama.world.edit`, `.validate`, `.undo`, `.redo`) shares that history with the editor. The editor (`prop-editor.ts`, with `EditToolbar.tsx` and `editor-input.ts`) is a toggled Edit mode, from a new button in the controls overlay; the world is not paused. **The owner restricted it to the normal window** (expanded mode), a departure from §12's "in-strip" editor: the strip's overlay has no Edit props button, and collapsing to the strip leaves Edit mode, committing a pending turn or scale, dropping a drag or a placement, and taking the preview away and showing the hidden prop again. Since the normal window takes focus (ADR 0016 §1), its keys work. Its toolbar sits in the top-left corner: a palette of the registered prop types, turn left and right, delete, undo, redo, and a line saying what a click does, or for 4 s why the last edit was refused (red) or what it warned about (amber: moved creatures, then the warnings, blocked exits among them). The palette needs the prop types on the main thread, so `ready`'s `WorldContent` gains `props` (each type's name, model and block radius), the one engine change. Protocol 15 hasn't been released, so its version stays (as in ADR 0015 §8). Every key also has a button: Delete or Backspace, R and Shift+R, Esc, Ctrl+Z, and Ctrl+Y or Ctrl+Shift+Z. Input is routed by capture listeners on the view's container, ahead of the camera's: only a press on the selected prop is the editor's (a drag there moves it); a press anywhere else orbits as before, and if it doesn't move it is a click, which selects the prop under it or, on bare ground, deselects. The wheel scales the selected prop by 1.1 a notch and zooms when nothing is selected; a double click doesn't reset the camera while editing. The editor never validates: every gesture commits one edit when it ends, and the edit's own checks answer it. A drag commits one `prop.move` on release, keeping the offset from the point grabbed to the prop's centre (not from the ground under the pointer, which behind a tree's crown can be metres away), and leaves the prop where the pointer last met the ground. Scale and turn (15° a press) are previewed and committed together 300 ms after the last notch or press, as one edit of a `prop.move` with only `rotationY` and a `prop.scale`; a drag started meanwhile takes them into its move. Undo, selecting another prop and leaving Edit mode commit a pending turn or scale first. While a gesture is shown, the original is hidden and a see-through preview drawn; after a commit the preview stays until the rebuilt props are drawn, so a prop never jumps back for a frame. Each edit the editor sends is tagged, and the values it sets are kept until it is drawn, so a gesture started before the redraw starts from them. The app takes a token when `world_changed` arrives (`worldChanged`: every edit applied so far, since an edit's answer comes before its `world_changed`) and hands it to `setProps` once `replaceProps` has drawn that change; only the edits it covers are done with, so with two edits in flight the first one's redraw keeps the second's preview and values. A refused edit forgets only its own values: the preview falls back to an earlier edit not drawn yet, or goes. A restore (`clear`) forgets every edit in flight, and an answer arriving after it changes nothing; `dispose`, with the view, drops a pending turn or scale and the timers. Placing from the palette previews the type under the pointer, a click places it and selects it (unless the world was restored or Edit mode left meanwhile), and placing ends there. A right-side prop drawer is to replace the palette's chips later. In the dev frontend an edit was answered in about 15–130 ms (it waits for the next tick).

### PR 7a: prop categories and thumbnails

The groundwork for the editor's prop drawer, whose tabs are prop categories and whose tiles show each prop type's model. A prop category is a content definition like a prop type (`PropCategoryDefinition`, schema version 1: `id`, `version`, `name`, the tab's label, and `order`) in a new `propCategories` registry, so a pack can add tabs. A prop type may name one category (`category`, a content ID; the prop schema version goes to 2, no migration). Its reference is checked like the prop's model and affordances, through `resolveReferences`, `addEntries` and `checkReferences`. The category is optional: an editor lists a prop type without one under "Other", which is not a registered category, so no engine or app code names a category ID. `sortedPropCategories(registries)` lists the categories in tab order: ascending `order`, then ID, so packs that pick the same order still list the same way. The built-in pack registers Trees (pine, round tree), Rocks, Plants (bush) and Mushrooms, with orders 10 to 40, leaving room between them. `world.json` is unchanged, since it names prop types, not categories. The worker doesn't send categories yet; the drawer's PR adds each prop type's `category` to the world content the worker sends and the sorted categories (`id`, `name`) beside it. The renderer draws thumbnails at run time, so no icon files are authored: `DioramaView.propThumbnail(model, size)` resolves to a PNG data URL of the model with that asset ref, `size` device pixels square (at most 1024), on a transparent background. It is the cue bubble's prop picture (`cue-icons.ts`, whose drawing is now shared as `drawIcon`): the same three-quarter view in plain daylight. It is drawn with the view's own renderer into a multisampled sRGB render target, read back, turned upright with straight alpha (unpremultiplied in linear light, so edges have no dark fringe) and encoded through a canvas. The models come from the view's `PropSet`, so a model the world already loaded isn't loaded again. Thumbnails are kept per model and size; each render target is freed once read. A ref with no model gets the fallback block, drawn once per size and shared by every such ref. The cache grows only with the refs and sizes asked for, until the view is disposed. After `dispose` thumbnails resolve to undefined.

### PR 7b: the prop drawer

The editor's palette chips give way to a prop drawer on the right of the normal window (`PropDrawer.tsx`, `prop-drawer.ts`). `ready`'s `WorldContent` gains `propCategories` (`id` and `name`, in `sortedPropCategories` order) and each `PropSummary` its optional `category`, the only engine change. Protocol 15 still hasn't been released, so its version stays, as in PR 6. The drawer shows while Edit mode is on, which is only in the normal window, and while it isn't closed: entering Edit mode opens it, and its close button and a toggle in the toolbar, where the chips were, close and reopen it, on the tab last shown. Closing it ends a placement, dragged or not, and keeps Edit mode, the selection and a pending turn or scale. It is a column beside the world view, not over it, so the view gets narrower and the renderer follows through its `ResizeObserver` on the container; the camera keeps its horizontal field of view, so the whole world stays in view, smaller. The overlay's buttons move left with the view's edge. The layout takes the drawer's width at once, so the view is resized once, and only the panel inside slides in, by a transform over 160 ms (not with reduced motion); it goes at once. Its tabs (`role="tablist"`, arrow keys, Home and End) are the categories in order, then Other for prop types without a category or with one that isn't registered; a tab with no prop types, Other included, isn't shown. Tiles list a tab's types by name. Each tile is a button with the type's thumbnail and name. Thumbnails (`PropThumbnails`) are asked for when a tab is first shown, only for its models, once each, at one size fixed when the view starts (56 CSS pixels × the device pixel ratio then), and never per frame (#198). A tile placed with a click works as the chips did. A press on a tile that moves more than 4 px drags the type (`TileDrag`): the tile captures the pointer, so the camera never sees the drag, and the editor's `startPlacingDrag`, `movePlacingDrag` and `endPlacingDrag` show the preview while the pointer is over the world view (the element under it is inside the view's container; the drawer and the toolbar aren't) and the ground, and place the type with one `prop.add` on release, selecting it, through the same commit as a click. Released over the drawer, the toolbar or off the ground, nothing is placed and placing ends. Esc, a lost pointer, closing the drawer and leaving Edit mode cancel a drag, and the click that ends a drag chooses nothing. The wheel doesn't zoom during a drag, so the ground under the preview stays put. A preview held for a placement not drawn yet stays while the next drag starts over the drawer (the editor has one preview, so the next drag's preview over the ground takes its place). While a placement is under way, a turn redraws its preview at once, and with a click placement the preview goes while the pointer is off the view (`pointerLeave`). The editor's input routing, commit tokens and held preview are unchanged.

## Consequences

- One pipeline with a full rebuild is simple and leaves no stale derived data, but its cost grows with the world. If larger worlds or terrain brushes make it too slow, an incremental or background rebuild replaces it behind the same command.
- A save of an edited world carries the whole world definition, so it is larger and no longer follows changes to the built-in world. That is what a user world needs, and the world library builds on it.
- Undo and redo are lost on relaunch, since only the edited world is saved.
- Structures and terrain are not editable yet; the op union and the full rebuild are where they join.
- Every edit makes every creature replan. Its cost and how it looks (a brief change of course is expected) are recorded in PR 2's "As built".
